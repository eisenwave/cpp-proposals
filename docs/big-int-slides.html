Introduction

std::big_int is an arbitrary-precision, elastic, numeric class type.

#include <big_int> std::big_int x = 1n << 1'000'000; // 21,000,000
arbitrary-precision
It has no fixed size. It can represent arbitrarily large integers (up to max_size()). If needed, dynamic allocations take place.
elastic
It grows and shrink as needed without explicit request to fit the result.

History

  • Several prior proposals tried to standardize std::integer:
    • [N1692] (2004), [N1744] (2005), [N2143] (2007)
    • all abandoned, despite positive reception
  • Meanwhile, arbitrary-precision integer support becomes the norm:
    • Builtin: Python, Ruby, Lisp, Scheme, Racket, Clojure, Haskell, Prolog, Wolfram Language, Maxima, Erlang, JavaScript, TypeScript
    • Standard library: Java, Kotlin, Julia, C#, F#, Visual Basic .NET, Go, Perl, Ada, Zig, Standard ML, MATLAB, PHP
  • third-party solutions like Boost.Multiprecision in C++

Motivation

  1. big_int is needed to represent large numbers
    • sometimes potentially big, sometimes actually big
    • serialization, scientific computing, cryptography, …
  2. big_int is a vocabulary type
  3. big_int enables rational, big_float, and big_decimal
  4. big_int makes correctness easy
  5. big_int is extremely platform-dependent and hard to implement
    • beman.big_int has > 1000 #if, #elif, and if constexpr

Design philosophy

  1. big_int should be easy to use and feel like int.
  2. big_int should be viable for almost all applications.
  3. big_int should allow the user to provide additional operations without overhead.
  4. big_int should have value-preserving conversions.
  5. big_int should be constexpr.

  • big_int is a small_vector with numeric operators
  • representation uses sign and magnitude, small object optimization

Why sign and magnitude?

Why mandate a representation? Why no implementation freedom?

  • necessary for consistent algorithmic complexity, noexcept
  • Example: operator- is 𝒪(1) with S&M, 𝒪(n) with two's complement

Why sign and magnitude in particular?

  • industry standard, also in Boost.Multiprecision
  • simpler +, -, *, / etc. — separate sign & magnitude calculations
  • negation and abs become 𝒪(1)
  • Downside: bitwise ops emulate two's complement on the fly

Small object optimization

  • Idea: store small integers in the container
  • Benefit: avoid heap allocations for small values
    • much more beneficial than for std::string
    • values outside 64-bit range are uncommon in many applications
    • zero memory access for small big_int passed by register
  • Cost: additional branches, more invalidation, possibly larger container
  • customizable via min_inplace_capacity parameter
    • default should typically be 64 for std::big_int
  • benchmarks: small big_int vs. builtin integer types

Accessing the limb array

span<const uint_multiprecision_t> representation() const noexcept;
  • Motivation: let user add big_int ops. without overhead
    • e.g. popcount(const big_int&) by counting bits in each limb
    • pointer can be passed to runtime library, possibly GMP
  • little-endian (least significant limb first) ⇒ cheap truncation/zero-ext.
  • Invariant: always canonicalized (no trailing zero limbs)
    • canonicalize once on write ⇒ avoid trimming on every read
  • invalidated by most operations, including move construction

Operators are complicated

  • ops should not wastefully allocate:
    • in (x+y+z), second addition should reuse alloc. of x+y
    • user gets performance benefits without mental effort
    • x|=y should modify limbs of x in-place if possible
    • for large _BitInt(N) operands, no temporary big_int created
  • different algorithms chosen at compile time:
    • use _BitInt if possible
    • use simple algorithms to keep more code in runtime library
  • different algorithms chosen based on limb count

Operators — Example of division

template<class L, class R> constexpr common-big-int-type<L, R> operator/(L&& x, R&& y);
  1. If constant-evaluated, delegate to _BitInt(N) division if available
  2. Otherwise, if both are single-limb, use builtin division operator
  3. Otherwise, if right operand is single-limb, use short division (#1, #2)
  4. Otherwise, if both are ≤ 128-bit, use __udivti3 for GCC and Clang
  5. Otherwise, if right operand is small, use long division (#3)
  6. Otherwise, use Burnikel–Ziegler sub-quadratic division
    (right operand ≥ 40 limbs on AArch64, ≥ 160 limbs on x86-64)
void short_div(span<u64> dest, span<const u64> x, u64 y); // #1 void short_div(span<u64> x_dest, u64 y); // #2 void long_div (span<u64> dest, span<const u64> x, span<const u64> y); // #3

Library support

Existing library facilities receive specializations/overloads:

  • std::hash (hashing the integer value)
  • std::numeric_limits (first class type to be supported)
  • std::in_range (but not std::cmp_*)
  • std::abs, std::gcd, std::lcm, std::midpoint
  • std::saturating_cast (but not rest of saturation arithmetic)
  • <charconv>, <format>, and std::to_string

<bit> support is omitted for now; consider e.g. std::countl_zero.

Case study — std::abs

template<size_t b, class L, class A> constexpr basic_big_int<b, L, A> abs(const basic_big_int<b, L, A>& j); template<size_t b, class L, class A> constexpr basic_big_int<b, L, A> abs(basic_big_int<b, L, A>&& j) noexcept;
  • all specializations supported, not just std::big_int
  • multiple overloads better than forwarding reference
    • only one instantiation for lvalues and const lvalues
  • noexcept because of sign and magnitude representation
    • std::abs clears the sign bit and returns j
  • does <cstdlib> provide std::big_int now?

Challenges specific to standardization

  • increased complexity of any future integer utility (like std::simd)
  • high implementation effort, especially for numeric parts
    • Possible solution: factor out portion into third-party component
    • beman.big_int has some hand-written assembly
    • precedent provided by Boost.Math
  • big_int ABI would be hard to change
  • big_int overloads bloat lightweight headers like <charconv>
  • ecosystem remains fragmented at first (see xkcd — Standards)

Implementation experience

  • full reference implementation at beman.big_int
  • heavily inspired by Boost.Multiprecision, but
    • constexpr out of the box, no union type punning
    • significant modernization using C++23, more lightweight
  • rigorously tested, 92% test coverage

Performance (benchmarks)

  • nearly uniformly better than Boost cpp_int
  • generally behind Boost gmp_int, but ahead across wide size ranges of some operations

Error handling

  • errors can be numeric errors or container errors
  • functions are noexcept if neither can occur

Numeric errors

  • Cause: division by zero, negative shift count
  • Effect: exception (std::domain_error), or a trap without exceptions

Container errors

  • Cause: exceeding max_size(), allocation failure
  • Effect: exception (e.g. std::bad_alloc)

Naming

std::big_int

  • almost every standard lib. in other languages uses big integer
  • std::integer is unclear, confusable with concept like std::integral

operator""n / operator""N

  • chosen for symmetry with JavaScript

std::uint_multiprecision_t

  • seems more fitting and focused than limb type
  • name deliberately long; type is necessary std::intmax_t-like evil

Future direction — What comes after P4444?

Language support

  • template<std::big_int>
  • better language support for operator""n
  • non-transient allocations (constexpr std::big_int variables)

Library support

  • new integer numeric functions (e.g. std::ipow)
  • additional constructors (e.g. from integer and exponent)
  • manipulating and iterating over individual bits
  • <random> support, possibly just distributions

⛔ Why no expression templates?

Idea: Expressions return a symbolic object (std::big_int_expre­ssion<...>) instead of std::big_int. This allows transformations:

abs(abs(x)) → abs(x) pow(x, y) % m → pow_mod(x, y, m)

Problems

  • increased complexity, maintenance burden, compile-time overhead
  • countless rules, special cases to be memorized by user
  • unreliable if optimizations optional, otherwise unfit for ISO process
  • bad interaction with auto, lifetime issues

⛔ Why no std::big_int_view?

Idea: Provide non-owning type (in addition or instead), similar to std::string_view.

Problems

  • big_int_view parameter cannot accept large _BitInt
  • provides not allocator for result
    • analogous to lacking operator+ between std::string_view
    • only read-only operations are possible, no +, -, *, /, etc.
  • provides no scratch space allocator

⛔ Why no std::big_uint?

Idea: Provide unsigned variant of std::big_int.

Problems

  • bifurcation of ecosystem and APIs
  • harmful to use of std::big_int as vocabulary type
  • storing sign bit is cheap ⇒ unsigned variant adds little value
  • overflow on subtraction
