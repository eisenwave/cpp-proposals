1. Introduction

The C++ standard library is currently lacking an elementary operation for decomposing floating-point numbers into integers. Such an operation is useful for a wide variety of applications, internally present in standard libraries already, and should be exposed to the user.

The C23 standard draft [N3220] describes the model of floating-point numbers in §5.2.5.3.3 as follows:

The following parameters are used to define the model for each floating type:

s sign (±1)
b base or radix of exponent representation (an integer >1)
e exponent (an integer between a minimum emin and a maximum emax)
p precision (the number of base-b digits in the significand)
fk nonnegative integers less than b (the significand digits)

For each floating type, the parameters b, p, emin, and emax are fixed constants.

For each floating type, a floating-point number (x) is defined by the following model:

x = s be ∑ k=1 p fk b−k , emin ≤ e ≤ emax

Or more simply and ignoring the exponent constraints, one could say:

x = s be q , q ∈ ℕ

This decomposition is not just a theoretical basis, but relevant in practice for implementing floating-point operations.

To implement std::scalbn(double x, int n) (which multiplies x with bn given n), one needs to

  1. decompose x into its floating-point components
  2. adjust the exponent by n, and
  3. recompose the floating-point number with the adjusted exponent.

To implement std::to_chars with output in hex notation, where b=2, one needs to:

  1. decompose the input into its floating-point components,
  2. bit-shift and convert the significand (integer) to hexadecimal digits,
  3. add/remove trailing zeros and/or insert a decimal point, and
  4. print 'p' followed by the (adjusted) exponent in decimal.

Of course, this is a gross simplification, and decomposing the floating-point number happens in decimal notation too, but there is a less direct relationship between the significand and the printed digits.

Frustratingly, this decomposition is already implemented in standard libraries, just not exposed to the user. It is also difficult for the user to implement this operation manually, especially with good performance. The standard library only offers much higher level operations such as std::frexp (which decomposes into a normalized fraction in ranges ±[0.5, 1) and an exponent); it does not provide the low-level building block that could be used to implement std::frexp, std::scalbn, std::to_chars, etc.

I therefore propose adding std::decompose_float function.

2. Motivation

The key benefit of a std::decompose_float function is that it allows the user to implement floating-point operations without needing special knowledge about the layout of the floating-point type.

When implementing a conversion from a float to a BigInt type (i.e. an arbitrary-precision integer), one would need to split the float into an integer q and binary exponent e, then

return BigInt(q) * pow(b, BigInt(q)); // << e for binary floats

This approach can be found in various arbitrary-precision arithmetic libraries in practice.

3. Design

The signature of the function is as follows:

template<class F> struct float_decomposition { private: static constexpr bool is-iec559 = numeric_limits<F>::is_iec559; public: // radix for the result of exponent() static constexpr int radix = numeric_limits<F>::radix; // lowest possible result of exponent() static constexpr int min_exponent_result = implementation-defined; // greatest possible result of exponent() static constexpr int max_exponent_result = implementation-defined; // greatest possible result of exponent() for finite values static constexpr int max_finite_exponent_result = implementation-defined; // greatest possible result of significand() static constexpr int max_significand = implementation-defined; // bit width of greatest possible significand() result, // which may be lower than the width of significand_type static constexpr int significand_width = implementation-defined; using significand_type = unsigned integer type; constexpr int sign() const noexcept; // returns -1 or 1 constexpr bool sign_bit() const noexcept; // returns std::signbit(x) constexpr int exponent() const noexcept; // returns base-radix exponent constexpr significand_type significand() const noexcept; constexpr bool is_finite() const noexcept requires is-iec559; constexpr bool is_inf() const noexcept requires is-iec559; constexpr bool is_nan() const noexcept requires is-iec559; constexpr bool is_normal() const noexcept requires is-iec559; constexpr bool is_signaling() const noexcept requires is-iec559; constexpr bool is_subnormal() const noexcept requires is-iec559; constexpr bool is_zero() const noexcept; }; template<class T> constexpr float_decomposition<T> decompose_float(const T& x) noexcept; // freestanding

A lot of design questions can be quickly answered in a few sentences:

Why is float_decomposition not simply an aggregate?
Because this gives the implementation more flexibility regarding the layout, including the use of bit-fields. Also, structured bindings would be undesirable due to potential bugs from getting the order of the members wrong.
Why is it constexpr?
Most floating-point operations (but especially inspection operations like std::isinf) are already constexpr, so this one should be as well.
Why is it freestanding?
The operation is elementary and does not raise any floating-point exceptions, nor does it interact with errno. There is no technical reason it couldn't or shouldn't be freestanding.
What is significand_type?
It is an implementation-defined unsigned integer type. This is needed because there are types such as std::float128_t where the result would not fit into other types like unsigned long long.
Why does exponent() return int?
Because int is sufficient for every real-world floating-point format, even if it has the minimum width of 16 bits. std::float128_t has only 15 exponent bits. The return type can be changed in the future should a floating-point format ever emerge that requires more than int can provide.
Why is radix provided as a static member?
Of all the numeric_limits properties, radix is the most important property in this context. It provides the minimum knowledge required for float_decomposition to be interpreted correctly. That justifies providing easy access to it.
Should float_decomposition not have a constructor?
No, the implementation might internally have a constructor, but there is no need to provide a user-exposed one. If there was a constructor taking, say, F, this would just create competing styles where some people skip std::decompose_float. Any other constructor provides pointless implementation work. As mentioned, there is a lot of representation freedom, so there might not even be a constructor, with all initialization taking place via std::bit_cast<std::float_decomposition>.

More involved design questions are addressed below.

3.1. Handling of non-finite inputs

Firstly, it should be noted that determining whether a number is finite is typically extremely fast and would be a side product of the decomposition process. ISO/IEC 60555 binary interchange floating-point types are non-finite if and only if the exponent consist of all one-bits.

The finiteness check for std::float32_t x within std::decompose_float boils down to:

// if (!std::isfinite(x)) if ((std::bit_cast<std::uint32_t>(x) << 1) >= 0xff000000) [[unlikely]] { // ... }

The bit_cast is essentially a no-op and performed anyway, the left-shift and integer comparison are extremely cheap operations, and the branch should be easily predictable, with the finite path being favored.

In the even that even this tiny check is too costly, it can be eliminated via [[assume(std::isfinite(x))]] up front.

The question is then what std::decompose_float should do for non-finite inputs. The most useful behavior were if

  • significand() simply returned the contents of the significand representation reinterpreted as an integer. This is useful for examining NaN payloads.
  • exponent() returned the exponent adjusted using the same bias as for finite numbers. For ISO/IEC 60559 binary interchange floating-point types, this means that the exponent of ±infinity would be greater than that of any finite numbers, which makes comparisons of exponent() between results meaningful, unless NaN is involved.

3.2. Why not a <cmath> function?

Another design option would be to go through WG14 and standardize a quantized function similar to frexp, like:

double frexpq(double x, int* exp) { // sample implementation assuming that numeric_limits<double>::radix == 2 double d = std::frexp(x, &exp); exp -= std::numeric_limits<double>::digits; return std::ldexp(d, std::numeric_limits<double>::digits); }

Unlike frexp, which returns a normalized fraction, this could return a number that is always a (small) integer. The significand integer can then be obtained via static_cast, and that conversion would always be exact given an integer with enough bits to represent the significand (except for non-finite inputs).

The key reason against this direction is that frexpq does only a portion of the work.

Consider how to actually implement a BigInt constructor as in the motivating example with BigInt in §2. Motivation using the hypothetical std::frexpq vs. the hypothetical std::decompose_float:

struct BigInt { // typical BigInt implementations use a sign-and-magnitude representation bool sign; unsigned long* limbs; BigInt(std::unsigned_integral auto value, bool sign) : sign(sign), limbs(do_alloc_limb_array(value)) {} #ifdef USE_FREXPQ BigInt(std::float64_t x) : BigInt(0, false) { if (!std::isfinite(x)) { throw std::invalid_argument("non-finite input"); } int e; double xi = std::frexpq(x, &e); *this = BigInt(static_cast<std::uint64_t>(std::fabs(xi)), std::signbit(xi)); *this <<= e; } #else BigInt(std::float64_t x) : BigInt(0, false) { auto d = std::decompose_float(x); if (!d.is_finite()) { throw std::invalid_argument("non-finite input"); } *this = BigInt(d.significand(), d.sign_bit()); *this <<= d.exponent(); } #endif BigInt& operator<<=(int s) { if (s > 0) do_shift_left(s); if (s < 0) do_shift_right(-s); return *this; } // ... };

The key observation is that std::decompose_float does the work of four functions simultaneously:

  • std::frexpq, by yielding the significand as an integer as well as the corresponding base-2 exponent;
  • std::isfinite, by identifying infinities and NaNs by their exponent;
  • std::fabs, by splitting the sign bit from the significand; and
  • std::signbit, by extracting the sign bit separately.

Miraculously, std::decompose_float is also a potentially cheaper operation than std::frexpq despite being vastly more useful. Specifically, std::frexpq would be required to normalize subnormal normals rather than merely adjusting the exponent like for normal numbers. By comparison, std::decompose_float can reinterpret the significand of both zeros and subnormal numbers directly.

In summary, std::decompose_float is the better solution for decomposing floating-point numbers because

  • it provides a cleaner interface; and
  • it is a swiss-army knife that tends to solve several problems simultaneously, like computing std::frexpq, std::fabs, and various boolean tests simultaneously; and
  • it does not waste any work, whereas std::frexpq needs to test whether a number is subnormal or infinity but stores an unspecified value in *e for such inputs (perhaps it could be defined not to waste this work, but std::frexp stores an unspecified value, so std::frexpq should presumably behave the same); and
  • it is easy to implement a variety of operations on top of std::decompose_float, but not on top of std::frexpq; for example, std::frexpq does not seem like it should be involved in std::signbit, but std::signbit(x) is std::decompose_float(x).sign_bit(); and
  • it has cheaper handling of subnormals because it can reinterpret the significand directly, suggesting that it is a lower-level or more elementary operation; and
  • it is safer: since std::frexpq requires the user to perform conversion to an integer type themselves, it presents a safety hazard if a user chooses an insufficient type and the conversion results in UB.

¶ Let x be the underlying value. Let b be radix.

¶ Effects:

  • If x is finite, exponent() returns e and significand() returns m respectively, such that | x | = m × be . Which combination of e and m is chosen is a property of the implementation, except that m is chosen to be representable in type T.
    [Note: Ignoring subnormal flushing, x equals copysign(scalbn(significand(), exponent()), T(sign())). — end note]
  • Otherwise, if T is an ISO/IEC 60559 binary interchange floating-point type and x is negative or positive infinity, exponent() returns max_exponent_result and significand() returns zero.
  • Otherwise, if T is an ISO/IEC 60559 binary interchange floating-point type and x is NaN, exponent() returns max_exponent_result and significand() returns the NaN payload of x, reinterpreted as an integer.
  • Otherwise, the result of exponent() and significand() is derived from x in an implementation-defined manner.

¶ Remarks: If two float_decomposition objects have the same underlying value, their respective exponent() and significand() results are equal.

¶ Recommended practice: If T is not an ISO/IEC 60559 binary interchange floating-point type but has similar representation, implementations should return the same results as if T were an ISO/IEC 60559 binary interchange floating-point type.
