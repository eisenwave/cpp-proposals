1. Introduction

For the purpose of implementing std::from_chars, all standard libraries have a function for accurately multiplying floating-point numbers by a power of 10. This is innately necessary.

Standard library Functions
libstdc++ from_chars_advanced →
fast_float::compute_float
libc++ __from_chars_floating_point_decimal →
decimal_exp_to_float
MSVC STL _Convert_decimal_string_to_floating_type →
_Assemble_floating_point_value

To understand how it is used, consider how "123.5" gets converted to a floating-point number:

  • "123.5" is parsed as an integer to 1235, with a base-10 exponent of -1. The mathematical value is 1235×10-1. Decimal digits past a certain point are simply ignored; the integer is formed from the most significant decimal digits in the string.
  • An internal function such as std::float64_t mul_pow10(std::uint64_t significand, int exponent) is called to calculate the result precisely, like mul_pow10(1235, -1). The function doesn't need to be correctly rounded, but it needs to be precise enough to ensure round-tripping between std::to_chars and std::from_chars, which requires proper results for at least 57 integer bits (but not correct rounding to 57 bits).

While multiplying with std::pow(10, exponent) ostensibly does the same, it is significantly less precise and overflows or underflows in cases where a std::mul_pow10 function wouldn't (like when combining a large significand with a hugely negative exponent).

In general, lots of floating-point operations exist solely to fuse other operations, like std::hypot, std::fma, etc.

2. Motivation

std::mul_pow10 is a necessary component of parsing floating-point numbers with round-tripping, is generally useful, and is incredibly hard to implement. std::from_chars can be seen as a higher-level wrapper, and if the user wants to make their own variant of std::from_chars which also supports digit separators and optional integer parts (e.g. to parse floating-point numbers in their own language), they have no means of skipping std::from_chars and going straight to the low-level numeric utility it wraps.

The implementation also involves large lookup tables, so even if the user implemented std::mul_pow10 themselves, they would end up pointlessly duplicating the lookup tables in the runtime library. This is a problem that only the standard can solve, not the ecosystem.

3. Design

3.1. API

We propose the following set of functions in <numeric>:

template<cv-unqualified-float F, signed-or-unsigned T> constexpr F mul_pow10(T n, int exp); template<cv-unqualified-float F, signed-or-unsigned T> constexpr F cr_mul_pow10(T n, int exp);

mul_pow10 computes n×10exp without correct rounding but with sufficient rounding for std::from_chars to round-trip for type F.

mul_pow10 computes the same with correct rounding, but it is implementation-defined which specializations are allowed (possibly none). Requiring correct rounding for all type combinations requires unreasonable implementation effort, but if the implementation provides a correctly rounded function anyway, it would be frustrating not to have any access to it. While such a function is innately not portable, the user can detect support using requires expressions.

3.2. Handling big integers

Since the API is constrained to accept any signed or unsigned integer type T, this raises the question how huge integers such as __int128 or _BitInt(1024) are handled. Correct rounding for mul_pow10 would impose an unreasonable implementation burden since in the worst case, every integer bit can affect the result; we cannot simply truncate the less significant bits.

However, mul_pow10 only needs to be sufficiently precise to ensure round-tripping, meaning that only a subset of integer inputs have a decent approximation.

For 128-bit integers and F = std::float64_t, 57 integer bits are sufficient for round-tripping. We can implement this specialization as follows:

using __u128 = unsigned __int128; using __i128 = signed __int128; float64_t mul_pow10(__u128 n, int exp) { // 1. Select the uppermost 64 nonzero bits in the input. int trunc_bits = max(64 - countl_zero(n), 0); auto m = uint64_t(n >> trunc_bits); // 2. Use the underlying mul_pow10 for uint64_t and float64_t, // with the same decimal exponent. // In practice, this function is correctly rounded, // i.e. cr_mul_pow10(m, exp) is available. float64_t trunc_result = mul_pow10(m, exp); // 3. Shift to the left // by the same amount that n has been shifted to the right. // Since float64_t is a binary float, // this operation merely adjusts the binary exponent // and introduces no further imprecision. return ldexp(trunc_result, trunc_bits); } float64_t mul_pow10(__i128 n, int exp) { // For any signed integer, // we can delegate to the corresponding unsigned implementation. if (n < 0) { // Unsigned negation guards against signed integer overflow. // copysign ensures that we produce negative zero on underflow. return copysign(mul_pow10(-__u128(n), exp), -1f64); } return mul_pow10(__u128(n), exp); }

This explanation may be inaccurate because if mul_pow10 underflows, ldexp does not produce the correct result.

This example is not specific to 128-bit integers and can be easily generalized to any width. The key insight is that while all integer bits would be necessary for correct rounding, only some of the leading bits are necessary for round-tripping, so any less significant bits can be truncated, for any integer width.

3.3. Why not use a floating-point operand?

One could also imagine a <cmath> operation like

std::float64_t scal10n(std::float64_t x, int exp);

However, this would not be sufficiently precise to implement std::from_chars. For binary64 format, at least 57 integer bits of precision are required for round-tripping, but std::float64_t can only represent 53 bits.

This is also why we don't propose a <cmath> operation that is C-compatible.

3.4. Decimal floating-point

Decimal floating-point numbers are a special case, and are somewhat supported by C++; numeric_limits<F>::radix may be 10, although there is no standard C++ spelling for decimal floating-point types, unlike C, which offers _Decimal64 et al.

The decimal case is usually trivial because it is always correctly rounded and can be implemented in terms of std::scalbn(_Decimal64(n), exp). Also, under the hood, ISO/IEC 60559 decimal floating-point types are an integer and decimal exponent, and any standard library providing support for them needs functions for converting between integers-and-exponent pairs and floating-point numbers. std::mul_pow10 is simply exposing those otherwise internal functions.

There is one edge case for decimal floating-point: huge numbers like those representable by _BitInt(1'000'000) may result in infinity when converted to _Decimal32, despite the mathematical result of, say, std::scalbn(_Decimal32(n), -10'000) being finite.

A robust approach that handles this case instead correctly rounds the input _BitInt(1'000'000) to however many integer bits fit into _Decimal32 and sets the exponent field.

// mostly freestanding namespace std { […] template<class T, class U> constexpr T saturating_cast(U x) noexcept; // [numeric.mul.pow10], multiplication with a power of 10 template<class F, class T> constexpr F mul_pow10(T n, int exp) noexcept; // freestanding-deleted template<class F, class T> constexpr F cr_mul_pow10(T n, int exp) noexcept; // freestanding-deleted }

[numeric.mul.pow10]

At the end of [numeric.ops], append a new subclause:

Multiplication with a power of 10 [numeric.mul.pow10]

1 In either of the following function descriptions, if the result is exactly representable in type F, no floating-point exceptions are raised; otherwise, the raised floating-point exceptions are a property of the implementation. Furthermore, if numeric_limits<F>::radix == 10 is true, the provided exponent exp is the preferred quantum exponent of the result.

template<class F, class T> constexpr F mul_pow10(T n, int exp) noexcept;

2 Constraints:

  • F is a cv-unqualified floating-point type ([basic.fundamental]).
  • T is a signed or unsigned integer type.

3 Constant When: The rounded result is finite and is zero if and only if n is zero.

4 Effects: If cr_mul_pow10<F>(n, exp) is well-formed, equivalent to: return cr_mul_pow10<F>(n, exp); Otherwise, returns n×10exp.

5 Remarks: If the result is not correctly rounded, let U be a hypothetical integer type so that any finite value x of type F can be decomposed into

  • a value m of type U and
  • a corresponding base-10 exponent e of type int

so that x equals mul_pow10<F>(m, e). The result of this function is at least as accurate as mul_pow10<F>(U(m), e) and depends solely on the unrounded result. The result has negative sign bit if n is negative.

[Example: mul_pow10<F>(42, 1) equals mul_pow10<F>(420, 0) because the unrounded result is 420. If F cannot represent 420, both these expressions are rounded to the same result. mul_pow10<F>(-1, -1'000'000) is negative zero if F has insufficient precision to represent the unrounded result. — end example]

The invention of a hypothetical integer type is necessary because we need to work with a type where the round-tripping requirement is actually feasible. Obviously, we cannot decompose a std::float128_t into a std::uint8_t and base-10 exponent; we need a fairly wide integer type for the significand.

However, we can require that the specialization mul_pow10<std::float128_t, std::uint8_t> is as precise as mul_pow10<std::float128_t, unsigned __int128> (possibly implemented by just calling that more precise function).

template<class F, class T> constexpr F cr_mul_pow10(T n, int exp) noexcept;

6 Constraints:

  • F is a cv-unqualified floating-point type ([basic.fundamental]).
  • T is a signed or unsigned integer type.
  • Either numeric_limits<F>::radix == 10 is true or the pair of types F and T belongs to an implementation-defined set for which this operation is supported. If the pair F and T belongs to this set and T is unsigned, then all pairs F and U belong to this set, where U is any integer type whose width is less than or equal to that of T.

7 Constant When: The rounded result is finite and is zero if and only if n is zero.

8 Returns: n×10exp correctly rounded.
