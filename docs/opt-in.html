1. Introduction

Kotlin has two commonly used annotations that have no C++ counterpart:

  • @RequiresOptIn creates an opt-in requirement for the annotated feature
  • @OptIn opts into use of declarations that require it

Library code:

@RequiresOptIn(message = "This API is experimental.") @Retention(AnnotationRetention.BINARY) @Target(AnnotationTarget.CLASS, AnnotationTarget.FUNCTION) annotation class MyDateTime @MyDateTime // A class requiring opt-in class DateProvider

Client code:

@OptIn(MyDateTime::class) // Uses DateProvider fun getDate(): Date { val dateProvider: DateProvider // ... }

The point of this feature is to let the user explicitly opt into features, such as experimental/unstable/nightly APIs that are part of the library, but which users should use with caution.

I propose to add a C++ counterpart to this feature, in the form of two attributes:

  • [[requires_opt_in(qualified-id, plain-string-literalopt, constant-expressionopt)]] creates opt-in requirement. This attribute can be applied to any declaration. The constant-expression controls the diagnostic level and/or disables the requirement.
  • [[opt_in(qualified-id)]] opts into a requirement.
  • [[export_opt_in(qualified-id)]] opts into a requirement and propagates that requirement to users of this declaration.

Library code:

namespace lib{ struct container { unsigned size(); [[requires_opt_in(lib::experimental_signed_size)]] int ssize(); }; }

User code:

struct wrapper { container c; unsigned size() { return c.size(); // OK, no opt-in requirement } // Propagate the opt-in requirement of the underlying library. // It's only possible to provide ssize() because the library does so, // so we should make users of wrapper::ssize() aware of this too. // // Alternatively, we could use 'opt_in' intead of 'export_opt_in' and promise // future compatibility, like using static_cast<int>(c.size()) at some point. [[export_opt_in(lib::experimental_signed_size)]] int ssize() { return c.ssize(); // OK, use of 'ssize' is in a context that opts in } } void f(wrapper w) { c.size(); // OK w.ssize(); // warning: opt-in 'lib::experimental_signed_size' required for 'ssize()' [[opt_in(lib::experimental_signed_size)]] w.ssize(); // OK, statement-level opt-in } [[opt_in(lib::experimental_signed_size)]] void g(wrapper w) { w.ssize(); // OK, function-level opt-in }

2. Motivation

Opt-in control annotations could provide a lot of utility, both to the C++ standard library and its implementations, as well as to third-party libraries.

2.1. Eliminating the std::experimental namespace

Currently, opting into TS features (that are not yet in the working draft) requires use of a std::experimental namespace. This is actually an opt-in in disguse, but not a great one. It makes it a breaking change to convert the TS code to standard code eventually, even if nothing about the API changed.

By comparison, the same could be accomplishing using a [[requires_opt_in(std::experimental)]] annotation.

2.2. Providing compiler extensions, including future standard extensions

For standard library vendors, the new attribute would make it very easy to extend the standard library with new inventions and with features that are only available in a more recent standard mode.

  • An [[opt_in(gnu::cxx29_extension)]] could be required to use C++29 features in older language modes, like C++26 and below, rather than eliminating these declarations entirely through #ifdef.
  • An [[opt_in(gnu::libstdcxx_extension)]] could be required to use vendor extensions in namespace std, like overloads of std::to_string for __int128.

Currently, providing such extensions is a risk to users who are trying to use only the features of the standard they are actually intending to use.

2.3. Quasi-deprecating flawed features

Some features in the standard may be considered undesirable, even if we never actually deprecate them because removal is not plausible.

std::rand is known for its low random quality, and could be annotated like:

[[requires_opt_in(std::low_quality_random)]] int rand(); [[requires_opt_in(std::low_quality_random)]] void srand(unsigned seed);

A user could still use rand(), but would need a [[opt_in]] attribute.

2.4. Providing opt-in mechanism for third-party libraries

Last but not least is the obvious use case: allowing library authors to mark certain experimental/unstable APIs as needing an opt-in. Currently, this would typically be done using the preprocessor, through various WANT_* and EXPERIMENTAL_* macros that may need to be defined before including a header.

This existing practice is a poor-man's solution because it requires an ever-increasing amount of conditional compilation. Preprocessing solutions also don't play nicely with modules; one can't customize modules by putting #define WANT_STUFF before import m;.

These solutions are also not capable of propagating opt-in requirements. Once some feature has been included via WANT, it's simply there, and the downstream consumers are not aware that they are indirectly using an unstable API. By comparison, [[export_opt_in]] can be used to propagate opt-in requirements, and such requirements can be propagated through the type system:

Core library:

namespace mathlib { using float8_t = /* ... */; // ... [[requires_opt_in( mathlib::decimal_float, "Support for decimal floating-point is experimental." )]] using decimal64_t = /* ... */; }

Linear algebra library:

namespace linalg { template<class T> struct vec3 { T x, y, z; // ... }; [[export_opt_in(mathlib::decimal_float)]] using vec3d64 = vec3<mathlib::decimal64_t>; }

Note that without the attribute on the declaration of vec3d64, a warning would be emitted.

Downstream user code:

void f(linalg::vec3d64 v); // warning: opt-in 'mathlib::decimal_float' required for 'vec3d64': // Support for decimal floating-point is experimental. [[opt_in(mathlib::decimal_float)]] void g(linalg::vec3d64 v); // OK

A a more concrete example, the Beman project provides reference implementations for various standard library proposals.

For those libraries, [[requires_opt_in]] could distinguish between features that are actually in the proposed wording and part of the current design, and features where the paper author is merely floating an idea and experimenting with design alternatives.

OpenGL essentially has two categories of functions:

  • Immediate-mode rendering functions like glBegin and glEnd.
  • Modern functions like glBindVertexArray.

While glBegin and glEnd are deprecated legacy OpenGL functionality, it makes little sense to make them [[deprecated]] in code. These functions are not going away anytime soon, and they do provide some toy graphics API for educational purposes which is very easy to use. Silencing [[deprecated]] would also require disabling e.g. -Wdeprecated entirely, which would be very bad.

However, it would be realistic for an OpenGL header or for some C++ wrapper to provide [[requires_opt_in(legacy_gl_api)]] so that old functions are not used accidentally.

3. Design

3.1. Controlling diagnostic level

The third parameter in a [[requires_opt_in(/* ... */)]] attribute is an optional constant-expression of type std::opt_in_requirement:

enum class opt_in_requirement { // Requirement is disabled. none, // Violation of the opt-in requirement results in a warning (default). warning, // Violation of the opt-in requirement results in an error. error, };

This level gives library authors more control, and is analogous to Kotlin's RequiresOptIn.Level, which is either ERROR or WARNING. The level also allows marking particular specializations as requiring an opt-in.

For a template result<T, E>, there are two ways to make the specialization result<void, E> require an opt-in:

// 1. Apply the requirement to the primrary template, // assuming that only that template is provided. template<class T, class E> struct [[requires_opt_in(/* ... */, std::is_void_v<T> ? std::opt_in_requirement::warning : std::opt_in_requirement::none)]] result { /* ... */ }; // 2. Alternatively, apply the requirement to some partial specialization. template<class E> struct [[requires_opt_in(/* ... */)]] result<void, E> { /* ... */ };

Without the extra requirement parameter, users would struggle with marking the use of specific template parameters as requiring an opt-in, such as when only const or volatile parameters require opt-in. This would be especially problematic for function templates, which don't support partial specializations.

3.2. When opt-in is required

Opt-in is required in the same cases where [[deprecated]] would emit a warning. For example, a deprecated overload in an overload set does not mean that the entire overload set requires opt-in.

When it has been determined that opt-in is required for some construct that refers to another construct, the opt_in_requirement value of the requirement is checked, and either nothing, a warning, or error is emitted.

3.3. Overload resolution and SFINAE

Even when the user specifies opt_in_requirement::error, this does not alter the result of overload resolution, and it is SFINAE-unfriendly. Any opt-in requirement is either satisfied, or the diagnostic is emitted.

3.4. Ignorability of attributes

A notable problem is that older compilers do not support [[requires_opt_in]], so even if a library author specifies opt_in_requirement::error, there is no strict guarantee of an error on lack of opt-in.

However, this problem is not a deal-breaker because

  • the library author cannot distinguish between a user whose [[requires_opt_in]] attribute is broken and between a user who opted in, so the functionality they are providing still needs to be correct for everyone, and
  • a library author could also guard opt-in features behind the __cpp_opt_in feature-test macro, so they only provide opt-in extras if users are reliably forced to opt in.

The feature-test macro is actually necessary to avoid warnings for unrecognized attributes, so all a library author has to do is:

#ifdef __cpp_opt_in [[requires_opt_in(/* ... */)]] void f(); #endif void f();

That is, they should make the whole declaration guarded by the feature-test, not just the attribute. Or alternatively,

// defined once #ifdef __cpp_opt_in #define MY_LIB_OPT_IN_FEATURE(id, msg, ...) \ [[requires_opt_in(id, msg)]] __VA_ARGS__ #endif // Expands to nothing of opting in is not possible, // or expands to a declaration with [[requires_opt_in]] MY_LIB_OPT_IN_FEATURE(stuff, "Experimental.", void f() { // ... } )

Of course, eventually support for [[requires_opt_in]] would be so widespread that these macro uses would no longer be necessary. Pure C++29 code would have no need for them. This may just take a few decades.
